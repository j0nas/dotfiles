# Dotfiles repo managed by chezmoi

## Key rules

- **Setup is idempotent.** `chezmoi apply`, `setup.sh`, and the `run_once_*` / `run_onchange_*` scripts must be safe to re-run: no duplicate appends, no clobbered user state, no crashes on existing installs.
- **Three OS targets**: macOS, Linux, and WSL. WSL is NOT the same as Linux — it has Windows-specific quirks (ConPTY, `/mnt/c`, symlinks don't cross OS boundary).
- **Don't hardcode usernames**. Use `{{ .chezmoi.username }}` in templates or `${USER}` in shell scripts.
- **chezmoi naming**: dotfiles use `dot_` prefix, templates end in `.tmpl`. Files in `.chezmoiignore` are repo-only (not applied).
- **`run_*` scripts live in `.chezmoiscripts/`** — a chezmoi special dir whose scripts execute but create no target file (keeps the repo root uncluttered). **Execution order is alphabetical by *stripped* name** (without the `run_*` prefix), across that whole dir: `run_once_bootstrap.sh.tmpl` must sort before `run_onchange_install-*.sh.tmpl` so the package manager exists before package install runs. (Note: relocating a `run_onchange_` script re-runs it once — its state key includes the target path — which is safe given the idempotency rule above; `run_once_` is keyed on content alone and is unaffected.)
- **All aliases go in** `dot_config/zsh/aliases.zsh.tmpl` — nowhere else.
- **Desk roles** — hardware pairings tied to one physical desk are self-contained dirs gated on a boolean in `.chezmoi.toml.tmpl` derived from the SHA-256 of the Mac's hardware UUID (`ioreg` IOPlatformUUID; only the hash is committed — a hostname drifts when macOS appends "-2" on a name clash), read as `(and (hasKey . "<flag>") .<flag>)` so a machine that hasn't re-run `chezmoi init` skips the desk instead of failing its apply. Their extra brews sit under `desk_<role>:` in `.chezmoidata.yaml` and join the Brewfile only when the flag is true. Gate on the role, never on the OS. Current: `g9_desk` → `dot_config/g9-desk/` (README.md there is the runbook; its `.chezmoiscripts` runner only re-runs `setup.sh` on change).
- **Shared data** lives in `.chezmoi.toml.tmpl` (`font`, `name`, `email`) and `.chezmoidata.yaml` (package + extension lists). Use template variables instead of hardcoding.
- **WSL → Windows paths** go through `{{ template "win-home" . }}` (`.chezmoitemplates/win-home`), never `/mnt/c/Users/${USER}`: the Windows account name needn't match the Linux one. `.chezmoi.toml.tmpl` resolves `win_home` from `%USERPROFILE%` (`cmd.exe` + `wslpath`) at `chezmoi init`; the partial falls back to `/mnt/c/Users/<username>` on a machine that hasn't re-run init.
- **WezTerm config** (`dot_wezterm.lua.tmpl`) is a chezmoi template. Use `wezterm.target_triple:find("windows")` for Windows-specific Lua logic. On WSL, this file is copied (not symlinked) to the Windows home by `run_onchange_after_sync-wezterm.sh.tmpl`.
- **VS Code settings** — the real content is the repo-only `Code-settings.json` (a static file, not a template; ignored in `.chezmoiignore`). Each OS gets a symlink to it via `symlink_settings.json.tmpl`: macOS at `private_Library/private_Application Support/Code/User/`, Linux/WSL at `dot_config/Code/User/`. `.chezmoiignore` gates which symlink applies per OS. The symlink means VS Code's own writes (Settings UI) flow straight back into the repo (auto-committed). On WSL, the settings are also copied to the Windows side by `run_onchange_sync-vscode.sh.tmpl`. Note: symlinked = not templated, so the font is hardcoded here rather than using `{{ "{{ .font }}" }}`.
- **SwiftBar** (menu-bar host for the AeroSpace workspace-label plugin) is configured headlessly — no GUI clicks. `run_onchange_after_setup-swiftbar.sh.tmpl` (darwin-gated, `after_` so it runs once the files below exist) writes the plugin folder to the `PluginDirectory` defaults key (SwiftBar stores it as a plain string and isn't sandboxed, so no security-scoped bookmark) and loads the login agent. Launch-at-login is a tracked LaunchAgent at `private_Library/LaunchAgents/com.ameba.swiftbar.autostart.plist` (`open -a SwiftBar`, `RunAtLoad`) because SwiftBar's own toggle is GUI-only `SMAppService`; the existing `.chezmoiignore` `Library` rule gates it to darwin. The plugin itself is `dot_config/swiftbar/plugins/executable_aerospace.sh` — the filename carries no refresh interval, so SwiftBar never polls it; it renders once at launch and then only on demand. The menu-bar update relies *entirely* on the `exec-on-workspace-change` hook in `dot_aerospace.toml.tmpl`. AeroSpace only reads its config at launch, so `run_onchange_after_reload-aerospace.sh.tmpl` (keyed on the config hash) runs `aerospace reload-config` on every apply that touches the config. With no poll fallback this is load-bearing, not a nicety: a dormant hook would leave the label frozen until AeroSpace restarts.
- **mise manages CLI tools** (declared in `dot_config/mise/config.toml`), converged by `run_onchange_after_install-mise-tools.sh.tmpl`, which installs missing tools then runs `mise upgrade` to roll loose pins (`node = "26"`, `"latest"`) to the newest matching release. It first runs `mise self-update` — mise itself is installed by mise.run into `~/.local/bin`, which no `mise install`/`upgrade` touches, so without it mise froze at its bootstrap version. That script carries **two** state keys: the config's hash *and* a Unix-week counter (`div (now | unixEpoch) 604800`). The hash alone only re-ran it on an edit, so `mise upgrade` almost never fired and every `"latest"` pin sat frozen at whatever it resolved to the day it was added; the week counter re-runs it on the first apply of each week. `minimum_release_age = "7d"` in the mise `[settings]` keeps those loose pins (and npm/pipx transitive deps) from resolving to anything published in the last week — a supply-chain cooldown; an exact pin bypasses it. Prefer this dual-key shape over a bare `run_` script for anything that should self-heal on a cadence — a bare `run_` would make *every* apply pay for a network round-trip per tool. The `after_` is also load-bearing: the script reads the **target** `~/.config/mise/config.toml`, so without it the run happens before chezmoi writes that file — the apply that first declares a tool logs "all tools are installed" against the stale config and skips it, yet still records its state key (computed from the *new* source config) as done, leaving the tool missing until an unrelated edit re-triggers the script. **Any converge script that reads a target file it also keys on needs `after_`.** GUI apps + VS Code extensions live in `.chezmoidata.yaml`, consumed by `run_onchange_install-packages.sh.tmpl` / `run_onchange_install-vscode-extensions.sh.tmpl`.
- **chezmoi manages itself.** `chezmoi = "latest"` in the mise config, so the weekly converge above rolls it forward. `setup.sh` still installs a bootstrap copy into `~/.local/bin` via `get.chezmoi.io` (a bare machine needs chezmoi before mise exists), but that's behind a `command -v` guard and never upgrades — and `~/.local/bin` *precedes* mise's shims on PATH, so it would permanently shadow the managed binary. The converge script deletes that bootstrap copy once `mise which chezmoi` resolves. Unlinking a running executable is safe on Unix (the open inode outlives the path), so the in-flight apply finishes on the old binary.
- **Node is managed by mise** directly (no fnm layer). The global default lives in `dot_config/mise/config.toml` (`node = "26"`); per-project switching uses a `mise.toml` pin, or `.node-version`/`.nvmrc`/`package.json` devEngines via the `idiomatic_version_file_enable_tools = ["node"]` setting in that same file. `mise activate` (in `dot_zshrc.tmpl`) auto-switches on cd. Use `mise use node@<v>` to pin a project, `mise use -g node@<v>` to roll the global default. Node must install before the `npm:*`-backed tools (their install shells out to npm), so the bootstrap and the mise-tools converge both run `mise install node` first.
- **`run_onchange_` vs `run_once_`**: anything tracking *desired state that can change* (tool lists, package lists, default versions) belongs in a `run_onchange_` script keyed on that state — embed `{{ include "file" | sha256sum }}` or reference the data var — so `chezmoi apply` re-converges when the declaration changes. Reserve `run_once_` for genuinely one-time bootstrap with no state to track: installing the package managers themselves, expensive one-shot downloads. Mutable desired-state in `run_once_` is a bug — it won't re-run when you change the declaration.
- **`run_once_bootstrap.sh.tmpl`** handles userspace bootstrap (Homebrew, mise). System-level installs (zsh) go in `setup.sh`. Anything downloaded outside a package manager gets a pinned version **and** a sha256 (Deskflow, the Linux Nerd Font in `run_onchange_install-linux-font.sh.tmpl`, the Obsidian Tasks plugin), with the pin in `.chezmoidata.yaml` or the script so a bump re-runs it. Anything that can live under `$HOME` as a plain download goes in `.chezmoiexternal.toml` instead (currently the two zsh plugins — no plugin manager): an `archive`/`file` entry with an exact release URL and `checksum.sha256`, which `validate` enforces (no `git-repo` externals, no `latest`/branch URLs).
- After editing wezterm config, run `chezmoi apply` to sync the Windows copy.
- **Config validation** lives in one script, `.githooks/validate` (the single source of truth), run by both the pre-commit hook and CI. It: renders every `*.tmpl` + `.chezmoiignore` (`chezmoi execute-template --source` — portable to CI) and keeps the output so later steps lint what chezmoi would really write; dry-run applies the whole source state into an empty dir (ignore rules, symlinks, the modify template, data files; encrypted/scripts/externals excluded); rejects source-state names (`dot_…`, `private_…`) in `.chezmoiignore`, whose patterns match **target** paths; checks every JSON is well-formed (`jq`); validates files with a published schema against the **pinned** vendored copies in `.githooks/schemas/` (`check-jsonschema` for JSON, `taplo` for TOML) and rejects top-level Claude settings keys the schema doesn't know unless allowlisted in `claude_unschemaed`; runs `shellcheck --severity=warning` on every shell script — chosen by **shebang** (plus any `*.sh`), so extensionless hooks and `executable_` bins are covered; bans bash-4 builtins in `#!/bin/bash` scripts; parses zsh configs (`zsh -nf`), plists (Label must equal the filename), Lua (`stylua` used only as a parser), Python (`ast`), the gitconfig (`git config --list`) and the workflow (`actionlint`); and checks every `skills/`/`commands/`/`rules/` entry has its `dot_claude/` symlink stub (skills/commands with frontmatter) and no stub into the repo dangles. All tools are mise-managed (CI apt-installs zsh on Linux). Notes: VS Code settings are syntax-only (no usable static schema); `shellcheck` threshold is `warning` (info-level SC2016/SC2086 are noisy/often-intentional); WSL-gated scripts render empty off-WSL and are skipped. Every check was negative-tested against a deliberately broken copy — do the same for a new one. `git commit --no-verify` bypasses.
- **Hook install**: `run_onchange_install-git-hooks.sh.tmpl` sets `core.hooksPath` to the tracked `.githooks/` (pre-commit = validate, post-commit = auto-push). `.githooks/`, `.github/`, `.taplo.toml` are repo-only (dotted source entries are auto-ignored by chezmoi). To refresh a schema, re-download into `.githooks/schemas/` (see its README).
- **CI** (`.github/workflows/validate.yml`): runs `.githooks/validate` on push/PR across a macOS + Linux matrix, so each platform's rendered templates get linted (the local hook only sees the committer's OS). Tools via `jdx/mise-action` + `mise use -g`; `chezmoi init --apply=false` first so template data resolves.
- **Shortcuts cheat sheet** (`SHORTCUTS.md`, repo-only) is generated by `.githooks/generate-shortcuts` from `# sc:` tags placed next to the real bindings. It's deliberately format-agnostic: it greps for the tag in any commentable file (toml/lua/zsh/…), never a tool's native binding syntax — so a brand-new tool needs **no code**, just tags. Grammar: `<comment-leader> sc: <trigger> | <description> | <section>` (section optional; the tool heading is derived from the source file via `toolname()`). The pre-commit hook regenerates + stages it so it never needs hand-editing, and `validate` asserts the committed copy matches (regenerate + `diff`) to catch `--no-verify`/CI drift. Tool *defaults* that aren't literal bindings (fzf chords, etc.) are documented with a hand-written `# sc:` comment near where they're enabled. `SHORTCUTS.md` is in `.chezmoiignore` (repo artifact, not applied); the `keys` alias opens it. A read-only copy is also published into the Obsidian vault at `Tech/Shortcuts.md` by `run_onchange_sync-obsidian-shortcuts.sh.tmpl` (keyed on the sheet's hash; vault path derived from `.obsidian_vault`) — a real file rather than a symlink because iCloud syncs links, not their targets, so the phone would see nothing.

## Claude Code skills, commands, secrets

- **Personal skills** live as real directories at `skills/<name>/` (repo-only — see `.chezmoiignore`). Each is surfaced into `~/.claude/skills/<name>` via a per-skill symlink file at `dot_claude/skills/symlink_<name>.tmpl` whose contents are `{{ .chezmoi.sourceDir }}/skills/<name>`.
- **Slash commands** follow the same shape: real `commands/<name>.md`, symlinked from `dot_claude/commands/symlink_<name>.md.tmpl`.
- **Editing a skill or command** via the `~/.claude/...` path edits the source file directly (it's a symlink). After editing, invoke `/dotfiles` to commit + push — chezmoi's autoCommit only fires on `chezmoi edit`, not on direct edits to source.
- **Third-party skills** installed by `pnpm dlx skills add` live at `~/.agents/skills/<name>` and surface into `~/.claude/skills/` as symlinks managed by the skills CLI — not by chezmoi. Coexist fine.
- **Secrets** are age-encrypted, decrypt via your SSH key. Sources are `dot_claude/private_secrets/encrypted_private_*.json.age` (private = mode 0600 on apply) → `~/.claude/secrets/*.json`. Recipients (machines authorized to decrypt) live in `.age-recipients` at the repo root — public keys, safe to commit; its header has the add/revoke + re-encrypt procedure. Edit with `chezmoi edit ~/.claude/secrets/<file>.json`, add with `chezmoi add --encrypt ~/.claude/secrets/<file>.json`. `age` is installed via the `brews:` list in `.chezmoidata.yaml`.
- **Claude Code settings** (`~/.claude/settings.json`) — Claude Code rewrites this file itself (`/config`, `/theme`, effort changes, onboarding prompts), so it is NOT a plain managed file: the managed keys live in the repo-only `Claude-settings.json` (root, `.chezmoiignore`d, schema-validated) and `dot_claude/modify_settings.json` is a chezmoi *modify template* that reads the live file from stdin and `mergeOverwrite`s the managed keys over it. Managed keys always win on apply, keys Claude writes that we don't manage survive, and apply never stops to ask about drift. To retire a key, add it to the `unset` list in the modify template (otherwise the stale local value lingers). `chezmoi status` may still show `MM .claude/settings.json` after Claude touches it — that's expected and harmless. `validate` schema-checks both the managed file and the rendered merge (`execute-template --with-stdin`). The model is left at the account default: `model` is in the `unset` list and not managed, so a `/model` pick lasts until the next apply. Effort is declared per model in the managed `modelSettings` (Opus 5 / 5.5 `xhigh`, Fable 5.1 `medium`), keyed by exact model ID — a new Opus release needs its own entry; every other model falls back to the top-level `effortLevel` (`medium`). `modelSettings` is in the `unset` list *and* managed, so the block is rebuilt from the repo on every apply — confirming a level with `/effort` saves it locally but the next apply reverts it. Override per session with `claude --effort <level>` or `s` in the `/effort` slider, not by editing the file.

## Package management

GUI apps and VS Code extensions are declared in `.chezmoidata.yaml` and consumed by `run_onchange_*` scripts that re-run when the data changes.

- **macOS** (`brew bundle` with `cleanup --force`) — strict declarative state. Removing a cask from the YAML uninstalls it.
- **VS Code extensions** — same: extensions not in YAML get uninstalled.
- **winget** (Windows) — install-only. Removing from YAML does NOT uninstall.
- **flatpak** (Linux) — install-only. Removing from YAML does NOT uninstall.

Trust the package manager — **never** add filesystem existence guards (`[[ -d /Applications/X.app ]]`, `command -v x.exe`). Install paths vary (`Program Files` vs `%LocalAppData%\Programs` vs `WindowsApps`) and go stale.

- `brew bundle` — exit 0, idempotent. ✓
- `flatpak install -y flathub X` — exit 0 + "already installed, skipping". ✓
- `winget install --id X` — **non-zero** exit (`0x8A150061`) if already installed. Must wrap in `|| true`.

Adding a new GUI app = one line in `.chezmoidata.yaml` per platform.
