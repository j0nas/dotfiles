## 3MF format reference

A 3MF file is a ZIP archive. Bambu Studio expects this structure:

```
[Content_Types].xml
_rels/.rels
3D/3dmodel.model                    # assembly: top-level objects + build plate items
3D/_rels/3dmodel.model.rels         # references to object model files
3D/Objects/object_N.model           # per-object mesh data (vertices + triangles)
Metadata/model_settings.config      # object/part names + extruder assignments
Metadata/project_settings.config    # full slicer/machine/filament settings
Metadata/slice_info.config          # client version header
Metadata/cut_information.xml        # cut data per object (stub OK)
Metadata/filament_sequence.json     # {"plate_1":{"sequence":[]}}
```

### XML namespace convention

3MF model files MUST use `p:` as the namespace prefix:

```xml
<model unit="millimeter" xml:lang="en-US"
  xmlns="http://schemas.microsoft.com/3dmanufacturing/core/2015/02"
  xmlns:BambuStudio="http://schemas.bambulab.com/package/2021"
  xmlns:p="http://schemas.microsoft.com/3dmanufacturing/production/2015/06"
  requiredextensions="p">
```

Components use `p:UUID`, `p:path`. Build items use `p:UUID`.

### Multi-color objects

Each top-level object in `3dmodel.model` has `<components>` referencing mesh parts in an object file. Each part gets its own extruder assignment in `model_settings.config`:

```xml
<!-- In model_settings.config -->
<object id="3">
  <metadata key="name" value="My Object"/>
  <metadata key="extruder" value="2"/>
  <part id="1" subtype="normal_part">
    <metadata key="name" value="Body"/>
    <metadata key="extruder" value="2"/>
  </part>
  <part id="2" subtype="normal_part">
    <metadata key="name" value="Accent"/>
    <metadata key="extruder" value="1"/>
  </part>
</object>
```

### Avoiding the "old version" warning

Without `Metadata/slice_info.config` and `Metadata/project_settings.config`, Bambu Studio shows a "generated by an old version" warning. Always include both. A saved H2C settings template exists at `C:/Users/jonas/Desktop/bambu/Filament Swatch/h2c_project_settings.config`.

The `slice_info.config` is minimal:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<config>
  <header>
    <header_item key="X-BBL-Client-Type" value="slicer"/>
    <header_item key="X-BBL-Client-Version" value="02.05.00.66"/>
  </header>
</config>
```

### STL to 3MF mesh conversion

To embed STL mesh data in a 3MF object file, parse the STL (ASCII or binary), deduplicate vertices, and write:

```xml
<object id="1" p:UUID="..." type="model">
  <mesh>
    <vertices>
      <vertex x="0.0" y="3.0" z="0.0"/>
      ...
    </vertices>
    <triangles>
      <triangle v1="0" v2="1" v3="2"/>
      ...
    </triangles>
  </mesh>
</object>
```

### CLI gotchas (macOS 02.08, hard-won)

- **`--arrange 1` is mandatory for programmatic 3MFs** (no plate block in
  model_settings.config): without it the CLI "succeeds" in ~2 s having sliced nothing.
- **Pass `--export-3mf` an absolute path** — relative paths resolve against Studio's own
  cwd and the file lands somewhere else.
- The sliced project stores its G-code as `Metadata/plate_1.gcode` inside the exported
  3MF — unzip and grep it to verify temps/settings actually applied.
- `[error] Invalid T command (T1001/T65535/T65279)` lines are benign — Bambu's own start
  G-code AMS commands upsetting their G-code analyzer.
- Exit 139 + `type must be string, but is array` right after load = a malformed value
  shape in project_settings.config (see the arity rules below).

## Per-layer temperature changes (temp towers) — what actually works

**Height-range modifiers CANNOT change nozzle temperature.** BambuStudio parses
`nozzle_temperature` inside `Metadata/layer_config_ranges.xml` without error and then
silently drops it before slicing: only `PrintRegionConfig` keys survive
`apply_to_print_region_config` (plus the special-cased `extruder` and `layer_height`),
and GCode.cpp never reads ranges. This is why naive tower generators need hand-edited
G-code.

What works — and what the GUI itself produces — is **per-layer custom G-code**:
`Metadata/custom_gcode_per_layer.xml`, one `M104` per floor boundary:

```xml
<?xml version="1.0" encoding="utf-8"?>
<custom_gcodes_per_layer>
<plate>
<plate_info id="1"/>
 <layer top_z="10.05" type="4" extruder="1" color="" extra="M104 S225" gcode="M104 S225"/>
<mode value="SingleExtruder"/>
</plate>
</custom_gcodes_per_layer>
```

- `type="4"` = CustomGCode::Custom (ColorChange 0, PausePrint 1, ToolChange 2, Template 3);
  the `extra` payload is emitted verbatim at that layer. Duplicate `gcode=` attr for parity
  with Studio's writer.
- Put markers at boundary **+0.05 mm** so they attach to the next floor's first layer at
  any layer height; an exact-boundary marker can fire one layer early.
- **The file only loads when `dont_load_config` is false** — the 3MF must carry
  `<metadata name="Application">BambuStudio-XX.XX.XX.XX</metadata>` in 3dmodel.model
  (unlike `layer_config_ranges.xml`, which loads unconditionally).
- Works fine with NO project_settings.config embedded: the user's own profiles apply and
  only layer 1 prints at their filament's first-layer temp.

## Multi-filament + per-layer temps: the clobber trap (H2C, verified 2026-08)

**Filament changes re-impose the profile temperature.** The machine's
`machine_change_filament_gcode` template resolves `new_filament_temp` placeholders at slice
time, so every swap emits `M104 T0/T1 S<profile temp>` — silently overwriting any per-layer
custom-G-code temps (`layer_z` IS available in that template context, so a conditional
corrective chain is technically possible, but fragile — don't). Consequences:

- A temp tower's floors CANNOT carry a second filament (each swap resets both heads to the
  profile temp; the preview still shows the stepped colours — it lies).
- Multi-colour is safe only where the intended temp equals the profile temp — e.g. features
  confined to the first floor of a tower (base-plate label inlay). Verified in G-code:
  swaps confined to the base layers, staircase intact, zero tool-addressed reheats after.
- On the H2C the CLI maps 2 filaments to separate heads (T0/T1 swaps + standby cooldowns
  `M104 T0 S25/S60`); grouping is Studio's "Auto For Flush" (`filament_map_mode`).

## project_settings.config array-arity rules (H2-series projects)

Value shapes are strict — get them wrong and load crashes (see CLI gotchas):

- Scalar keys must stay scalars (`description`, `printer_settings_id`…). Wrapping a
  scalar in an array = `type must be string, but is array` crash.
- Per-filament keys: array length == project filament count (N).
- On H2 series, ~43 keys (incl. `nozzle_temperature`, `nozzle_temperature_initial_layer`,
  most `filament_*`) are per-filament × hotend-variant: length = N × the machine's
  hotend-variant union (see below), interleaved (`filament_self_index` = 1,1,2,2,…).
- `flush_volumes_vector` is per-filament × EXTRUDER (2N) — same length as the variant
  interleave on 2-variant machines, NOT the same key family. `flush_volumes_matrix` is
  N²×2 (both extruders). Machine per-extruder keys are length 2, `printable_area` /
  `wrapping_exclude_area` are coordinate lists — leave those alone when resizing slots.
- Only include keys a real project save contains; profile-only extras (`description`,
  `include`, `filament_extruder_compatibility`…) crash or pollute the strict loader.

**Combo arity is PER-NOZZLE, not fixed at 4** (learned 2026-08-07 the hard way). Process
and machine per-variant vectors are indexed by the machine's (extruder, hotend-variant)
enumeration — `printer_extruder_id` × `printer_extruder_variant`:

- H2C 0.2/0.4/0.8: 4 combos `[1-Std, 1-HF, 2-Std, 2-HF]`; filament-variant union 2.
- H2C 0.6: **5 combos** `[1-Std, 1-HF, 1-E3D, 2-Std, 2-HF]`; filament union 3 (`[S,HF,E3D]`,
  `filament_self_index` = 1,1,1 for one filament). `machine_max_*` are combo PAIRS
  (combos × 2 → length 10 on 0.6).
- The stock "Bambu Lab H2C 0.4 nozzle.json" machine file carries the 5-slot superset (it's
  the inheritance parent of 0.6); 0.2/0.8 override back to 4; real 0.4 saves use 4. The OTA
  dir (`~/Library/Application Support/BambuStudio/system/BBL`) can hold a STALE 4-slot
  profile set — trust real project saves over either profile dump.
- **The sync trap**: a project whose vectors are self-consistently SHORT (e.g. 4-slot on
  0.6) slices fine in the CLI and in the GUI pre-sync — but when Studio syncs with a
  physical printer, it converts every vector to the machine's native enumeration and fills
  missing (extruder, variant) combos FROM THE SYSTEM PRESET, silently replacing project
  values (formeriet's flow tower lost its per-floor wall speeds to stock 500 mm/s this way:
  constant cap-limited flow, no bands, on High Flow hotends). Fill EVERY slot — including
  in `layer_config_ranges.xml` option values.
- Verification trick: unzip a REAL project saved from a synced session on the target
  machine and diff array lengths key-by-key against the generated export (formeriet used
  `~/Desktop/projects/3d/bambu/temp-tower-petg-260-210.3mf` as the 0.6 ground truth).
- `filament_extruder_variant` is the machine-side enumeration — never copy it from a
  filament profile (stock profiles carry a bogus single-entry list).

To go from 1 filament slot to N: duplicate per-filament entries, expand per-filament×variant
groups `[v0,v1]` → `[v0,v1,v0,v1,…]`, resize the flush matrix to N²×extruders, and set
`filament_self_index` to `1,1,2,2,…`. An arity manifest generated at collapse time is the
only reliable way to tell a collapsed per-variant key from a genuine per-extruder machine
key — both are length 2.

**Reference implementation:** formeriet's `packages/tool-temp-tower` — `src/threemf.ts`
(complete validated project writer incl. custom G-code) and `scripts/flatten-settings.mjs`
(collapses a project-settings template's filament slots and flattens Generic profile
inheritance chains from the local Studio install). A working multi-part / two-filament-slot
variant (per-part extruders, arity-manifest slot expansion) lived at formeriet commits
75c41cf..60da6f8 before being removed — the clobber trap above kept breaking floor 1 of the
temp tower whenever the user swapped filament presets; dig it out of history if ever needed
for a NON-calibration multi-colour project, where preset-temp reheats are harmless.

## OrcaSlicer H2C exports crash Bambu Studio (verified 2026-08-07)

Orca 2.5.0-dev (nightly, first H2C support) `.gcode` / `.gcode.3mf` exports segfault
Studio 02.08.01.55 on open — EXC_BAD_ACCESS in `GCodeProcessor` (`process_filament_change`
null `m_nozzle_group_result` / `get_machine_config_idx` indexing empty `extruder_types`).
Root cause: Studio's producer whitelist only accepts "generated by BambuStudio" (all other
producers are commented out in `GCodeProcessor::Producers`); Orca's "generated by OrcaSlicer"
header means `process_file` resets state, skips the CONFIG_BLOCK apply, and the H2-series
dual-extruder arrays stay empty until the first `T`/`G1` dereferences them.

Fix (verified in GUI): rewrite the producer line to `; generated by BambuStudio 02.08.01.55`.
For `.gcode.3mf` that's the line inside `Metadata/plate_*.gcode`, and `plate_*.gcode.md5`
must be regenerated (uppercase hex MD5 of raw bytes). `scripts/fix_orca_h2c_for_studio.py`
(this skill) does both, plus syncs `project_settings.config` `filament_map` to
`slice_info.config`'s `filament_maps` — Orca writes `["1","1"]` there even when the plate
was actually sliced onto the left head (`filament_maps "2 1"`, Auto For Flush).

Debug techniques that paid off: parse `~/Library/Logs/DiagnosticReports/BambuStudio-*.ips`
(JSON after line 1; faultingThread frames are symbolized) instead of re-crashing blind, and
crash-test GUI-only load paths headlessly via `open -a BambuStudio <file>` + polling for new
.ips files. Caveat: the open event is dropped when the app is cold-starting — "no crash" only
counts if Studio was already running. Studio also pops a benign "generated by a newer
version, values replaced" dialog for Orca-only enum values (`rectilinear` → zig-zag etc.).

Gotcha found the same day: Orca's calibration wizard slices with whatever machine variant the
printer dropdown has — check `; printer_variant` in the export before trusting a calibration
(a 10–40 mm³/s max-flow test sliced against the 0.2-nozzle profile is garbage on 0.4 hardware).

Second failure mode (same day, PETG/0.6 High Flow export): with the producer patched, Studio
instead showed "Failed to process the G-code file ... from previous 3mf" — a caught exception
in `Print::export_gcode_from_previous_file`, which re-runs a FRESH GCodeProcessor whose only
3mf-derived input is the nozzle-group context rebuilt from `slice_info.config`. Orca's
new-format markers (`<nozzle id="1" extruder_id="2" .../>` + `group_id` on `<filament>`) with a
single-entry `filament_maps "2"` (one filament on the left head) produce a context Studio's
processing throws on; the PLA/Standard file's `filament_maps "2 1"` shape survived. Bisected
via A/B hybrid 3mfs — swapping gcode body/config did nothing; wrapper metadata was the trigger.
Fix (in the fixer script): strip the `<nozzle>` element + `group_id` attrs from slice_info so
Studio takes its backward-compat path (extruder count from `nozzle_diameters`, see
`MultiNozzleUtils.cpp` nozzle-list builder). Verified: PETG 0.6 High Flow file then loads.
Also: Studio 02.08 frequently crashes ON QUIT (malloc "pointer being freed was not allocated")
— ignore shutdown .ips reports when counting load-crash evidence.

## Python + 3MF gotchas

### Do NOT use xml.etree.ElementTree for 3MF

Python's ElementTree mangles namespace prefixes (`ns0:UUID` instead of `p:UUID`), producing files Bambu Studio rejects or loads incorrectly. Use string-based XML generation instead.

### OpenSCAD ASCII STL detection

Check for `solid` keyword at start AND `facet` within first 1000 bytes. Some binary STLs happen to start with `solid` in the header, so checking both avoids misdetection.

## Geometry-only import silently strips custom G-code (verified 2026-08-07, v02.08.01.55)

A 3MF with the `Application: BambuStudio-*` tag but NO loadable
`Metadata/project_settings.config` triggers Plater's "The 3mf is generated by old Bambu
Studio, load geometry data only." dialog (`load_config && config_loaded.empty()`), and the
geometry-only path **skips `plates_custom_gcodes` adoption** — per-layer custom G-code is
silently dropped. The CLI does NOT reproduce this (no CheckVersion strategy, no dialog):
CLI slicing shows the markers working while every GUI open loses them. Consequences:

- "Markers ride along without embedded settings" is FALSE for GUI users. Every project
  export must embed a COMPLETE project_settings.config.
- A partial config is no fix: Plater applies it over `FullPrintConfig::defaults()`, so
  missing keys become slicer defaults, not the user's presets.
- Also stamp the settings `version` key (a template save carries its own old version).

Per-nozzle H2C variants (formeriet `packages/bambu-project`, `flatten-settings.mjs`):
flatten the machine-variant + standard-process inheritance chains, diff against the
collapsed 0.4 template, adapt arities. Two traps found the hard way:

- **Never let the diff carry `*gcode*` keys**: the machine chains bottom out in
  BambuStudio's built-in defaults (Ender-style prime line at hardcoded 205 °C, X1-style
  end block), not the real machine G-code — the template save's genuine blocks must win.
- **Rewrite `print_compatible_printers`** to the variant machine name, or slicing fails
  with "process not compatible with printer".

Flow contract note: deposited cross-section is Slic3r's rounded rectangle
`(w−h)·h + π(h/2)²` (measured via E-per-mm in sliced G-code, all nozzles within 1–2 %) —
naive `w×h` overstates volumetric flow by ~11 %.

## layer_config_ranges.xml — per-height PrintRegionConfig that actually slices (2026-08-07)

Format (parsed unconditionally, unlike custom G-code): `<objects><object id="N">` where N is
the **1-based model object index** (not the 3MF object id), then
`<range min_z=".." max_z=".."><option opt_key="..">value</option></range>`. Three rules paid
for in debugging:

- Only PrintRegionConfig keys survive (speeds, widths); `nozzle_temperature` parses and is
  silently dropped (why temp towers need per-layer M104 instead).
- **Every range must include `layer_height`** — Slicing.cpp does
  `option("layer_height")->getFloat()` with no null check → exit-139 segfault in
  `layer_height_profile_from_ranges` on ranges without it. The GUI's range editor always
  adds one; programmatic writers must too.
- **Vector options need the machine's FULL combo arity** (per-nozzle — 5 on H2C 0.6, 4 on
  0.2/0.4/0.8; see the arity rules above): `outer_wall_speed` is
  ConfigOptionFloatsNullable; a bare "78" deserializes to a 1-slot vector, the
  extruder-variant lookup misses, and the range silently falls back to the global value
  (no error, wrong print). A 4-slot "78,78,78,78" on the 0.6 machine fails the same way
  AFTER printer sync (the missing (2,HF) combo gets the system preset's speed). Serialize
  one value per combo: "78,78,78,78,78" on 0.6.
- Spiral/vase mode refuses ranges outright: "The spiral vase mode does not work when an
  object contains regions with different print settings" — choose one.

Also: Studio's preview simulates M104 (Temperature view shows bands) but NOT M220 feedrate
factors — an M220-based speed tower previews as constant flow even though firmware steps it.
For preview-true speed steps, use ranges. Reference: formeriet `packages/tool-flow-tower`.
